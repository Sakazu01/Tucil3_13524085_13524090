\section{Pendahuluan}

Ice Sliding Puzzle adalah permainan pencarian rute pada papan es. Aktor berawal dari tile \texttt{Z} dan harus mencapai tile tujuan \texttt{O}. Pada setiap aksi, aktor memilih arah \texttt{U}, \texttt{D}, \texttt{L}, atau \texttt{R}, lalu terus meluncur sampai tepat sebelum menabrak dinding \texttt{X}. Gerakan tidak valid apabila aktor keluar papan, melewati lava \texttt{L}, melewati checkpoint angka yang belum sesuai urutan, atau berhenti di goal sebelum semua checkpoint selesai.

Setiap tile memiliki cost traversal. Cost satu gerakan adalah jumlah cost semua tile yang dilalui selama sliding, tidak termasuk tile posisi awal sebelum gerakan. Karena itu, solusi dengan jumlah gerakan paling sedikit belum tentu merupakan solusi dengan total cost terkecil.

Program dibuat dengan backend Go dan frontend HTML/CSS/JavaScript. Backend membaca testcase, memvalidasi papan, menjalankan algoritma pathfinding, dan mengirimkan hasil serta frame visualisasi ke GUI.

\section{Pemodelan Permasalahan}

\subsection{State dan Goal}

Satu state pencarian direpresentasikan sebagai:
\[
  n = (\text{posisi aktor}, \text{checkpoint berikutnya})
\]
Posisi aktor menyimpan baris dan kolom saat ini. Checkpoint berikutnya menyimpan indeks checkpoint terkecil yang belum dilewati. State awal adalah posisi \texttt{Z} dengan checkpoint berikutnya bernilai 0. State goal tercapai jika aktor tepat berhenti di \texttt{O} dan seluruh checkpoint sudah dilewati sesuai urutan.

\subsection{Pembangkitan Successor}

Dari sebuah state, program mencoba empat arah gerak. Mekanisme sliding berjalan tile demi tile sampai aktor menabrak dinding. Jika gerakan valid, posisi tepat sebelum dinding menjadi state baru. Jika aktor keluar papan, melewati lava, atau melewati checkpoint yang belum sesuai urutan, successor dibatalkan.

Cost successor dihitung dari akumulasi cost tile yang dilalui selama gerakan. Urutan ekspansi arah yang digunakan program adalah \texttt{U}, \texttt{D}, \texttt{L}, lalu \texttt{R}.

\section{Algoritma Pathfinding}

Notasi yang digunakan mengikuti materi Route Planning. \(g(n)\) adalah cost dari start ke state \(n\), \(h(n)\) adalah estimasi cost dari state \(n\) ke target, dan \(f(n)\) adalah fungsi evaluasi yang menentukan prioritas ekspansi.

\subsection{Uniform Cost Search}

Uniform Cost Search (UCS) memakai priority queue berdasarkan cost aktual:
\[
  f(n) = g(n)
\]
Langkahnya adalah memasukkan state awal dengan \(g(n)=0\), mengambil node dengan \(g(n)\) terkecil, mengecek apakah node tersebut goal, lalu membangkitkan successor dari empat arah. Untuk setiap successor valid, program menghitung \(g'(n)=g(n)+\text{cost gerakan}\) dan memasukkannya ke priority queue. Karena cost tidak negatif dan ruang state berhingga, UCS lengkap dan optimal terhadap total cost.

\subsection{Greedy Best First Search}

Greedy Best First Search (GBFS) memakai prioritas:
\[
  f(n) = h(n)
\]
GBFS memilih state yang terlihat paling dekat ke target menurut heuristik. Program tetap menyimpan \(g(n)\) untuk menghitung cost akhir, tetapi nilai tersebut tidak memengaruhi prioritas ekspansi. GBFS sering meninjau state lebih sedikit, tetapi tidak menjamin solusi optimal karena cost yang sudah ditempuh diabaikan.

\subsection{A* Search}

A* memakai gabungan cost aktual dan estimasi:
\[
  f(n) = g(n) + h(n)
\]
Setiap successor diberi prioritas berdasarkan total cost yang sudah ditempuh ditambah estimasi cost tersisa. Jika heuristik admissible, A* dapat menemukan solusi optimal. Dalam program ini, A* dapat memakai H1 Manhattan, H2 Minimum Slide, atau H3 Dijkstra.

\subsection{Bonus: BFS}

Breadth First Search (BFS) memakai queue FIFO dan mengekspansi state berdasarkan kedalaman. Pada puzzle ini, BFS mencari solusi dengan jumlah gerakan sliding paling sedikit. BFS tidak optimal terhadap total cost ketika tiap tile memiliki cost berbeda.

\subsection{Bonus: IDA*}

Iterative Deepening A* (IDA*) memakai \(f(n)=g(n)+h(n)\), tetapi menjalankan DFS dengan threshold. Threshold awal adalah \(h(\text{start})\). Jika goal belum ditemukan, threshold dinaikkan ke nilai \(f\) terkecil yang sebelumnya melewati batas. IDA* hemat memori, tetapi dapat mengekspansi ulang state pada iterasi threshold berikutnya.

\section{Heuristik}

\subsection{H1: Manhattan Distance}

H1 menjumlahkan Manhattan distance dari posisi aktor ke checkpoint berikutnya, antar checkpoint yang tersisa, lalu dari checkpoint terakhir ke goal. Jumlah jarak tersebut dikalikan dengan cost walkable minimum:
\[
  h_1(n)=\left(\sum \text{jarak Manhattan target tersisa}\right)\times \text{minCost}
\]
H1 murah dihitung, tetapi sering terlalu optimistis karena tidak memperhitungkan rintangan dan aturan sliding.

\subsection{H2: Minimum Slide}

H2 menghitung jumlah slide minimum untuk mencapai target berikutnya melalui BFS ringan pada state puzzle, lalu mengalikannya dengan cost walkable minimum:
\[
  h_2(n)=\text{minSlideToNextTarget}(n)\times \text{minCost}
\]
H2 lebih sadar terhadap aturan sliding dibanding H1, tetapi tetap lebih ringan daripada H3.

\subsection{H3: Dijkstra ke Target Berikutnya}

H3 menjalankan Dijkstra dari state saat ini menuju target berikutnya dengan aturan sliding dan cost asli. Jika masih ada checkpoint, targetnya adalah checkpoint berikutnya; jika checkpoint sudah habis, targetnya adalah goal. H3 lebih informatif, tetapi lebih mahal karena melakukan pencarian internal pada setiap evaluasi heuristik.

\subsection{Admissibility}

Ketiga heuristik yang digunakan pada A* bersifat admissible dengan asumsi cost tile walkable tidak negatif. H1 adalah lower bound karena setiap rute valid harus menempuh minimal jarak Manhattan antar target dan setiap tile memiliki cost minimal \(\text{minCost}\). H2 adalah lower bound karena setiap slide valid melewati minimal satu tile dengan cost minimal \(\text{minCost}\). H3 adalah lower bound karena hanya menghitung cost minimum menuju target berikutnya, sedangkan solusi penuh dari state tersebut harus setidaknya mencapai target berikutnya sebelum selesai.

Dengan demikian, heuristik tidak melebih-lebihkan cost sisa menuju goal. H3 biasanya paling kuat, H1 paling murah, dan H2 berada di tengah.

\section{Source Program dan Cara Menjalankan}

Source program terdapat pada folder \texttt{src}. Struktur utama program:

\begin{verbatim}
src/backend/algorithm   UCS, GBFS, A*, BFS, IDA*, dan heuristik
src/backend/engine      Parser, board, state, dan mekanisme sliding
src/backend/main.go     HTTP server dan endpoint API
src/frontend            GUI visualizer
test                    Testcase .txt
dox                     Laporan LaTeX
\end{verbatim}

Program dijalankan dengan:

\begin{verbatim}
.\run.ps1
\end{verbatim}

Script tersebut menghentikan proses lama pada port \texttt{8080}, lalu menjalankan:

\begin{verbatim}
go run ./src/backend
\end{verbatim}

Setelah server hidup, GUI dibuka melalui \url{http://localhost:8080}. Pengujian laporan ini memakai \texttt{go1.25.4 windows/amd64}.

\section{Analisis Hasil Percobaan}

Pada testcase kecil seperti \texttt{testcase1.txt}, semua algoritma menemukan solusi dengan cost dan jumlah move yang sama. Ruang state yang kecil membuat perbedaan iterasi belum terlalu terlihat.

Pada \texttt{testcase6.txt}, BFS menemukan solusi 13 move dengan cost 218, sedangkan UCS dan A* menemukan cost 217 dengan 14 move. Ini menunjukkan bahwa solusi dengan move paling sedikit tidak selalu memiliki total cost paling kecil.

GBFS sering lebih hemat iterasi. Pada \texttt{testcase9.txt}, GBFS-H2 hanya meninjau 74 iterasi, sedangkan UCS meninjau 311 iterasi. Namun, cost GBFS-H2 adalah 1385, lebih besar dari UCS dan A*-H2 yang menghasilkan cost 1313. GBFS-H1 bahkan menghasilkan cost 2046. Hal ini sesuai teori bahwa GBFS cepat tetapi tidak optimal.

A* menghasilkan cost yang sama dengan UCS pada seluruh testcase solvable yang diuji. Pada \texttt{testcase9.txt}, A*-H2 mengurangi iterasi dari 311 menjadi 240, dan A*-H3 menurunkannya lagi menjadi 149. Walaupun begitu, H3 tidak selalu menjadi waktu tercepat karena perhitungan heuristiknya menjalankan Dijkstra internal.

\texttt{testcase10.txt} adalah kasus tanpa solusi. Semua algoritma yang diuji mengembalikan \texttt{Found = Tidak}. Iterasi yang sama terjadi karena goal terisolasi dan ruang state reachable kecil.

\section{Kesimpulan}

Program berhasil memodelkan Ice Sliding Puzzle sebagai pencarian state dengan aturan sliding, checkpoint berurutan, lava, dan cost traversal. UCS menjadi pembanding optimal berbasis cost. GBFS cenderung cepat tetapi tidak optimal. A* dengan heuristik admissible mempertahankan optimalitas UCS sambil mengurangi ekspansi pada beberapa testcase. Bonus yang dikerjakan mencakup GUI, algoritma tambahan BFS dan IDA*, serta dua heuristik tambahan selain heuristik utama.
